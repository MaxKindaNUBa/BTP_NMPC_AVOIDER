A field note on state estimation

Chasing the Current

How a small autonomous boat learns its true speed through the water, and the ocean current quietly shoving it sideways — from four instruments that never measure either one, built up from nothing, then traced into the real filter running this project.

01 Instruments

Four instruments, two blind spots

Picture a small unmanned boat holding a course. It carries a GPS receiver, a compass, a rate gyro, and an accelerometer — a fairly ordinary sensor suite. Each one has a flaw, and the flaws are the whole plot.

The GPS doesn't report your exact position, it reports a position near it — jittering sample to sample, and on top of that jitter, quietly wandering off in one direction for a while before wandering back, the way a shadow drifts through a courtyard over an afternoon. The compass does the same to heading. The accelerometer is the strangest of the four: it doesn't just add noise to the acceleration it measures, it reads from a zero-point that has physically shifted from true zero — a real electrical offset baked into the chip — and that offset itself drifts, slowly, over minutes.

None of that is unusual for real hardware. What matters here is what's missing. Nothing on this list reads the boat's own speed — how fast it's actually moving through the water. And nothing at all reads the current: the slow, steady push of moving water that isn't the boat's doing, that no compass or accelerometer is built to notice, but that silently steers the boat off its intended track all the same.

Both of those — the boat's true speed, and the current pushing on it — are things this project needs to know well. Neither is on the instrument list. They have to be figured out from the four signals that are, and figured out well enough to hand back to the autopilot every tenth of a second. That's the job an Unscented Kalman Filter (a UKF) does here, and the rest of this note builds up, from nothing, exactly how.

02 Belief

A belief you can draw

Start with the simplest possible version of the problem: you want to know one number — say, the boat's speed — and you have two sources of information about it that each come with some uncertainty. Maybe you had an estimate from a moment ago, aged forward a little (your prior belief). Maybe a sensor just reported a new reading (your measurement). Neither is exact. How do you combine them?

A Kalman filter's answer starts with a shift in what you're willing to call "an estimate." Instead of a single number, it carries a whole little bell curve — a most-likely value (the mean) and a width around it (how sure it is). A wide bell curve is a shrug; a narrow one is confidence.

That's the update in one dimension. In two or more dimensions the same bell curve becomes an ellipse — a cloud with a shape, not just a width, because uncertainty in one direction is often tangled up with uncertainty in another. A single GPS fix, for instance, tells you a lot about where you are along the line the fix constrains, and comparatively little about your position along that line — so the cloud narrows sharply in one direction and barely at all in the other.

03 The bend

When the world bends

All of that works cleanly when the relationship between what you're estimating and what you observe is a straight line — push a bell-curve cloud through a straight-line function and you get another clean bell-curve cloud out, no drama. A plain Kalman filter only knows how to do that one trick, so it only works where the world genuinely is that simple.

This boat's dynamics aren't. The hydrodynamic force on the hull — the drag, the lift off the rudder, the thrust from the propeller — climbs with relative velocity in a curve, not a straight line: double the speed and the force does not simply double. That's ordinary fluid dynamics, and it means the function connecting "the boat's state right now" to "the boat's state a tenth of a second from now" is a genuinely bent one.

The classic fix, used by the Extended Kalman Filter (EKF), is to linearize: at today's estimate, draw the straight tangent line that just touches the real curve, and use that line's slope as a stand-in for the whole function. Close to the point you drew it at, the tangent and the curve agree closely. Get an uncertainty cloud with any real width, though, and its outer edges sit further from that point — and the further out you go, the more the straight-line stand-in and the real curve disagree.

That disagreement doesn't throw an error. The EKF just reports a mean and a spread that no longer quite match the real, bent physics — usually more confident than it has any right to be. The question the rest of this note answers is: what if you never approximate the curve at all?

04 Sigma points

Sample the cloud, not the function

Here's the idea the Unscented Kalman Filter is built on, and it's a genuinely different move: instead of approximating the function with a tangent line, approximate the cloud with a small, deliberate set of sample points — then push every one of those points through the real, exact, unmodified physics, individually. No curve-flattening anywhere. The only approximation left is which finite handful of points you chose to stand in for the whole cloud, and that handful is chosen specifically to get the cloud's mean and spread exactly right going in.

These sample points are called sigma points, and the recipe for placing them is almost stubbornly simple: put one point exactly at the mean, then, for every direction of uncertainty the cloud has, place one point a calculated distance out along that direction and a mirror-image point the same distance back the other way.

Placing the points is only half the trick. The other half is what happens next: every single sigma point gets pushed, on its own, through the real nonlinear model — the actual curved physics, not a tangent-line stand-in for it. Some points land further from where a straight-line guess would have put them than others, because the curve bends differently in different places. That's the point.

05 One cycle

One full turn of the crank

Put predict and correct together with sigma points doing the work, on a toy version of this exact problem: two unknowns, your own speed u and the current c pushing on you, and one noisy accelerometer reading that depends on both together (only the combined, water-relative motion produces force).

Predict

Take the five sigma points standing in for today's belief about [u, c], and age each one forward through the process model — roughly steady, plus a little uncertainty for what might genuinely change tick to tick. The reconstructed cloud comes out a little wider than it started: this is the "spread grows" half of the predict/correct loop from §02.

Correct

Now the real accelerometer reports a number. Before comparing, ask each of the five predicted sigma points what accelerometer reading it would produce — run every one through the sensor model, same as the dynamics. That gives a predicted-measurement cloud alongside the state cloud, and, crucially, a picture of how the two co-vary: do points with a higher u and points with a higher c tend to produce similar predicted readings, or does only one of them really move the needle?

The gap between the actual sensor reading and the predicted-measurement cloud's mean is the innovation — literally, the new information this tick contributes. The Kalman gain is what turns that gap into an actual correction: it reads the tilt of the joint cloud and asks, "for this much of a surprise in the measurement, how much should u shift, and how much should c?"

Blend prior and gain-weighted innovation, and the posterior lands where the diagram shows it — shifted, and narrower than the prior, because a real measurement just arrived. Run this predict-correct pair once every tick, forever, and that's the entire filter. Everything from here is what changes when you scale it up to twelve unknowns and six real sensors.

06 This project

Aboard this project

The toy carried two unknowns. The filter actually running here (ukf/ukf_core.py) carries twelve, and every one of the extra six exists for a specific, load-bearing reason.

The reasoning behind that last group is the sharpest idea in the whole project, and it's worth sitting with. If the filter has exactly one channel of evidence for some hidden quantity, and that channel has an unmodeled error riding along with it, the filter cannot tell the real signal apart from the error — it has nothing else to compare against. Whatever the error looks like gets absorbed into the hidden quantity almost whole.

That's the design. What follows is what happened when three of the numbers behind it were wrong — found and fixed in this project, in this order.

Bug one: a process-noise budget 7,147× too generous

Every predict step, the filter is told how much the current is allowed to have genuinely changed since last tick — a process-noise setting, q_diag. That number had been computed from a stale copy of the current model's own drift rate, then compounded by an earlier automated retuning pass, and came out roughly 7,147× the physically correct value. Told it could wander a hundred times faster than the real current ever does, the filter did exactly that — not because anything was noisy in the world, but because its own rulebook said wandering was allowed.

Bug two: confident, but confidently wrong

The obvious next step — correct that number, and while at it, tighten the filter's opening assumption about the current too — backfired the first time it was tried. The filter had always been seeded believing the current started at exactly zero. That's a reasonable, humble assumption when the filter is also willing to admit it might be very wrong (a wide opening cloud). Make it confident and keep the wrong starting guess, though, and the filter now believes strongly in something false — and takes far longer to talk itself out of it than a wider, humbler guess ever would have.

Bug three: going straight is close to the worst case

One more wrinkle, straight out of §05's Kalman-gain picture. The accelerometer only ever senses relative motion — water-relative velocity — which is the boat's own speed u minus the current pushing on it. Whenever the boat is running straight, that's the only combination of u and current the sensor can pin down. Their difference stays tightly constrained; exactly how that difference splits between "boat" and "current" individually stays almost completely open — nothing in a straight-line run tells you which one to credit.

A turn breaks the tie. Turning changes the geometry relating heading to sensed acceleration, which opens a second, differently-angled constraint — and where a tight band and a new, differently-tilted band cross, both unknowns are finally pinned down together, the same "two clues intersecting" idea from §05's gain picture, just spread across time instead of within a single tick.

One more deliberate choice belongs here. This project also runs an automated search that retunes several of the filter's noise settings by checking statistical self-consistency (a metric called NEES) against many random seeds. That search now leaves the current states alone entirely — on purpose. NEES only checks whether the filter's reported uncertainty matches its actual error; it cannot tell a genuinely uncertain estimate from an inflated one hiding a mistake. That is precisely how the 7,147× bug got there in the first place. So the current states keep their physically-derived numbers, full stop, regardless of what the automated search finds for everything else.

Where it landed

Both against a true current sitting near 0.1 m/s and 0.0 m/s respectively — the filter now tracks a signal that size to well under a millimetre per second, tick after tick, for the length of the run.

§ Appendix

Field glossary

The same ideas, under the names they go by in ukf/ukf_core.py and ukf/config.py.

sigma point
One of the 25 sample points standing in for the 12-dimensional belief cloud each tick — built and propagated inside predict(), held in the array X/Y.
α, β, κ
The three shaping dials from §04 — UKFConfig.alpha/beta/kappa, set to 0.001 / 2.0 / 0.0.
process noise, Q
How much each state is allowed to have genuinely changed since last tick — q_diag. The bug in §06 was this number, ~7,147× too large for the current states.
measurement noise, R
How much to trust a given sensor reading — r_diag, sized from the sensor's real datasheet.
innovation
Actual sensor reading minus the predicted-measurement mean — computed each tick in correct() as innovation.
Kalman gain, K
The tilt of the joint state/measurement cloud, turning an innovation into a state correction — K in correct(), built from the cross-covariance Pxz and Pzz.
P0
The opening belief's spread, before any measurement — p0_diag. Tightening this for the current states only helped once the seed (below) was also fixed.
seed
The opening mean itself — set in ukf_node.py's _seed(), now the current's own configured average instead of always zero.
NEES
Normalized estimation error squared — a self-consistency check used by tune_ukf.py's automated search, deliberately not allowed to touch the current states (§06).
